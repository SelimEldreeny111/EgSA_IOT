# WIOT STM32F401 Arduino firmware

This reference documents the **Arduino STM32F401 node and LoRa gateway** in
`Node/IoT_Node_Encrypted`. It covers the first-party application, communication,
radio, power-management, platform, configuration, and sensor modules. Bundled
ModbusMaster/nanopb sources, generated protobuf declarations, and private
configuration files are intentionally excluded.

## System boundaries

The build selects a sensor-node or LoRa-gateway role in `src/config/AppConfig.h`.
The sensor node samples an enabled product profile (TUF + HNDA or Supmea +
Sondas), prepares protobuf status/telemetry, encrypts it, and delivers it by
MQTT or LoRa. The gateway receives LoRa traffic, applies its routing checks,
and forwards encrypted payloads to MQTT. Command handling follows the reverse
path. Sensor selection, communication transport, watchdog policy, and component
power modes are compile-time choices; private broker, topic, and key values live
in files excluded from this reference.

### Sensor-node data path

1. `setup()` initializes board peripherals, the watchdog, RTC, RS485 bus,
   selected sensor drivers, and the active communication transport.
2. `loop()` services communication and power-state machines. When sampling is
   due, the flow-meter and soil-sensor drivers update `AppRuntimeState`.
3. The payload mapper copies valid measurements and quality indicators into
   nanopb messages. The packet codec serializes and encrypts the message.
4. MQTT or LoRa publishes the result; the delivery outcome informs the power
   manager and the next publish interval.

### Main module groups

| Directory | Responsibility |
| --- | --- |
| `src/app` | Startup orchestration, runtime state, flow profile selection, and Supmea period totals. |
| `src/config` | Compile-time product, identity, pin, transport, watchdog, and power policies. |
| `src/devices` | RS485 arbitration, four sensor drivers, RTC, and battery ADC. |
| `src/comm` | MQTT transport, command dispatch, protobuf payload mapping, and encrypted packet codec. |
| `src/radio` | E32/AS32 LoRa framing, addressing, and link operation. |
| `src/power` | Component sleep policy, command window, standby request, and wake handling. |
| `src/platform` | Hardware watchdog initialization and bounded servicing. |

## Important invariants

- Only one product profile is selected per firmware image; individual sensor
  switches within that profile determine which Modbus requests are sent.
- An enabled sensor is not necessarily valid. Publish validity flags convey
  whether the latest acquisition succeeded.
- The MQTT topic node ID and protobuf `node_id` must agree. A mismatch is
  rejected by the server even when encryption and decoding succeed.
- The current AES-CBC envelope has no authentication tag, and its IV is not
  generated by a cryptographically secure random source. Do not infer message
  integrity or resistance to active attackers from successful decryption.
- The watchdog must be serviced only while the main control path is making
  progress; long network and peripheral waits must remain bounded.
- Supmea calendar totals depend on RTC trust and persisted accumulator state;
  TUF period totals are read from the meter directly.
- Controller standby is supported only for combinations documented in the
  [power-down guide](POWER_DOWN_MODE_USER_GUIDE.md).

## Build and generate this reference

Open the Arduino sketch in this directory using the STM32 Arduino core and
board settings in the [project README](README.md). A firmware build also needs
local `src/config/AppConfig.cpp` (network/topic values) and
`src/config/AppSecrets.h` (AES key). Both are Git-ignored and deliberately
excluded from the published reference; never commit live credentials. Doxygen
generation does not need either file. To regenerate the API
reference, install Doxygen 1.14 or newer and Graphviz, then run from this
directory in PowerShell:

```powershell
.\generate_doxygen.ps1
```

Open `Documentation/Doxygen/html/index.html`. Doxygen also writes XML for
tooling and `Documentation/Doxygen/warnings.log` for documentation QA. The
generated directory is local build output; regenerate it from the checked-in
source and `Doxyfile` after code changes.

For commissioning and behavioral tests, consult the
[flow-profile and consumption guide](FLOW_METER_PROFILES_AND_CONSUMPTION_GUIDE.md)
and [power-down guide](POWER_DOWN_MODE_USER_GUIDE.md).
